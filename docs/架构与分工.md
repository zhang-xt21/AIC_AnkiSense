# 架构与分工

AnkiSense 是独立仓库，集中管理网页、后端、文档处理和自有 Anki 插件。Anki 官方程序独立安装，不在本仓库修改其源代码或复习调度算法。

## 当前链路

```text
选择 PPT / PPTX / PDF
   ↓ 后台转换、文字提取 / OCR、保存来源版本
结合原文与原页提取知识 → 生成卡牌 → 对照原页检查、必要时修正
   ↓ 自动展示结果，引用原页附在答案侧
检查通过：自动批准                  有疑点：保留草稿和原因
   ├─ 网页作答 → AI 诊断 → 原文依据与补充练习
   └─ APKG / 本机同步插件 → Anki 复习
```

默认入口为 `POST /api/material-imports`。选择文件后自动启动完整流程，无需先逐页确认或再次点击生成；局部失败保留说明并继续其余内容。自动通过的卡牌使用 `approval_method=automatic`，并通过 `automatic_evidence` 绑定卡牌内容、当前引用与原页检查。卡牌自动批准不把来源页标成人工校对，也不代表整页原文已经纠正。接口、状态和验收限制见 [自动制卡接口与验收](自动制卡接口与验收.md)。

网页和 FastAPI 服务在本机运行，SQLite 保存导入任务、制卡检查点、材料、卡片、作答及历史快照。PPT / PPTX 依赖本机 PowerPoint 或 LibreOffice 转换为 PDF，PPTX 同时提取原生文字；PDF 使用文字层或本机 OCR。默认自动制卡向已配置且支持图片输入的云端模型发送原文与对应原页，用于知识提取和卡牌检查；答案侧附上完整引用原页，不依赖 Docling 精确裁图。

「学习材料」中的「高级工具」保留可选手动流程：PDF / 粘贴文字 → 校对来源、手选片段或整份批量生成 → 制卡工作台编辑、配图 → 人工批准。高级批量任务默认 `autonomous=false`，生成结果均为草稿；该流程的整页来源确认要求不属于默认自动导入的前置步骤。高级图块推荐使用独立 `.venv-docling` 环境在本机分析，主动开启视觉检查时才发送候选裁图与原页。作答诊断目前以文字为依据，不自动理解卡片图片。

## 模块边界

| 模块 | 主要位置 | 职责 |
| --- | --- | --- |
| 网页交互 | `ankisense/static/`，其中 `automatic.js` 管理自动导入与卡牌结果 | 文件选择即启动、任务轮询与刷新恢复、卡牌展示；高级制卡、练习、导出和模型设置；展示后端状态，不自行决定批准与评分结果 |
| API 与数据 | `app.py`、`db.py`、`schemas.py`、`paths.py` | 请求、校验、事务、版本与本机路径；数据库默认在被忽略的 `data/` |
| 自动导入与制卡 | `automatic_import.py`、`presentations.py`、`auto_cards.py`、`automatic_runner.py` | 上传与格式转换、后台任务、分批生成和检查、保存检查点与重启恢复；高级手动任务与默认自动任务共用卡牌结构 |
| 来源与 OCR | `ingest.py`、`ocr.py`、`sources.py`、`source_calibration.py`、`source_policy.py`、`evidence.py` | 文字/OCR 提取、原页和来源版本；可选整页校准、人工确认；逐字引用与来源有效性 |
| 卡牌质量与批准 | `auto_card_models.py`、`card_quality.py`、`automatic_policy.py` | 知识和质量检查结构、重复与内容检查；绑定当前卡牌和来源的自动原页批准政策，区分机器检查与人工确认 |
| 图片处理 | `media.py`、`docling_adapter.py`、`figure_*.py` | 保存图片、Docling 图块、上下文、候选推荐与可选视觉检查 |
| AI 与作答 | `llm.py`、`prompts.py`、`model_settings.py`、`attempts.py` | 生成、诊断、模型配置、证据校验、调用失败与回答记录 |
| Anki 接口 | `plugin_api.py`、`plugin_sync.py`、`apkg.py` | v1 本机鉴权接口、导出与同步数据契约；不直接写 Anki 学习库 |
| Anki 插件 | `addons/ankisense_sync/`、`examples/anki_plugin_client.py` | 本机连接、下载与校验、Anki Collection API 写入、冲突提示与复习进度保留 |
| 验证工具 | `tests/`、`tools/` | 离线回归、浏览器检查、安装构建及额外环境验收 |

表中 Python 文件名均相对于 `ankisense/`。后端协议详情见 [插件接口 v1](插件接口说明.md)。接口已支持回答提交能力，但当前安装插件的用户界面只实现同步；网页作答链接仍会打开浏览器。

## 建议分工

按人数与经验分配以下职责；它们是责任边界，不是三个各自独立的产品：

- **界面与体验负责人**：制卡工作台、练习导航、图片展示、键盘与窄屏体验，同时维护相关前端与浏览器测试。
- **服务与集成负责人**：API、数据库版本、模型配置、同步与导出，对跨模块契约变更负责。
- **文档与效果负责人**：OCR、图块推荐、人工标注案例、模型诊断质量与验收报告，协同调整算法实现。

每项任务仍指定一个作者和一个评审者。数据库结构、插件协议、审核规则、卡片身份和来源快照属于共同依赖，修改前先把请求/响应或行为示例写进 Issue，再分配两端实现。不要同时让多个任务重写整个 `app.py` 或 `static/app.js`。

## 团队共享与本机状态

仓库共享源码、锁定依赖、自编示例和脱敏测试资料。模型密钥、讲义原件、学生回答、SQLite、Anki 资料和下载模型属于每个人的本机状态，不通过 Git 同步。

本次整理建立了新的源码目录，未复制旧开发目录的学习数据。第一次启动将创建自己的空学习空间。若以后确有迁移个人数据的需求，应先停止对应服务、备份完整数据并单独迁移；不要让两个运行中的服务共同写同一份数据库。

## 最终桌面形态

统一桌面客户端是后续产品目标，尚未确定要使用 Anki 插件扩展界面、维护 Anki 源码分叉或其他桌面容器。先通过真实用户流程确认需要解决的窗口切换问题，再评估开发成本、接口兼容与维护方式。现有文档、制卡、配图和诊断能力继续作为可复用模块。
